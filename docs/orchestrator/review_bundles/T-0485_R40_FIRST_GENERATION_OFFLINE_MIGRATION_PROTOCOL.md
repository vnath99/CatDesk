# T-0485 R40 — First-generation offline Wake migration protocol for review

Date: 2026-10-16. Source baseline: `b3427e9f2c4ce6f9e8b8b185e1a71fc6f3dd811f`. Status: `DESIGN_FOR_INDEPENDENT_REVIEW`, with no install authority. This record resolves a specific design mismatch; it is not an approval, a bootstrap record, or a claim that the historical connected store has been found.

## Why the present transaction cannot admit the offline predecessor

`wake/src/install_broker_approval.rs` requires nonzero `old_host_pid` and `old_host_creation_time_100ns` in every signed V1 package approval. `wake/src/install_broker_ledger.rs` requires a COMPLETE protected predecessor before a fresh successor and unconditionally leaves `first_generation_migration_anchor_verified` and `old_live_owner_verified` false. Those are correct refusals for the existing schema. The current dev.84 snapshot has no matching named process, but that snapshot does not prove global process absence, identify the historical connected root/lock, or authorize substituting the direct `%LOCALAPPDATA%` store. An offline migration must have its own reviewed first-generation path; fabricating a PID or setting either ledger boolean from `CatDeskWakeLegacyOwnerAudit` would defeat the protection.

The typed package publisher and `record_published` already exist in source as of `56536c2`/`002c792` and are covered by R31. The pre-install migration anchor, owner disposition, protected pointer switch, installed-reader cutover and provisioned service are the remaining transaction seams. R30/R39 statements that the native rename is test-only describe earlier source and must not be used as the current code inventory.

## Proposed trust inputs and explicit decisions

1. A separately provisioned fixed broker service runs from the compiled service path with a protected image, service SID, namespace and policy. A protected administrator provisioner must record image, service configuration, DACL, policy key and root physical identities and prove that the restricted worker and descendants cannot write or replace them. The fixed broker reads these objects itself. A package, local CLI caller or diagnostic report cannot choose its trust root or service path.
2. An independent reviewer approves a **first-generation migration anchor**, distinct from the package approval. Its purpose-specific signed bytes bind the selected dev.84 pointer object and exact canonical bytes, selected runtime root/`host.lock` physical IDs, selected immutable dev.84 image object and hash, protected destination root/policy/service identities, target conversation ID/generation/digest, desired running/stopped state, the disposition of every ambiguous or unresolved wake event, an install generation, and the intended dev.85 package manifest digest. The record explicitly names `CONNECTED_LIVE` or `REVIEWED_OFFLINE` (and, if necessary, an operator-reviewed *abandonment* of an irretrievable connected store). It has a unique ID, bounded validity, reviewer identity and a separate signature domain. The reviewer must inspect the source evidence; the broker must independently reobserve physical objects and state before it accepts the record. A hash of a diagnostic report alone is insufficient.
3. For `CONNECTED_LIVE`, the exact old owner must be observed in its **connected context**: pinned PID plus creation time and loaded image, actual runtime root/lock handles and byte-range-lock ownership, target generation, desired state and pending/ambiguous events. Dev.84 lacks the new nonce challenge, so a live case needs a separately reviewed, independent old-owner proof method. Until it exists, live migration refuses.
4. For `REVIEWED_OFFLINE`, no old PID is represented. The reviewer must choose one exact predecessor or explicitly approve abandonment; this choice cannot be inferred from the current caller's direct pointer. During the transaction the broker pins *all* known direct/connected candidate roots and lock objects with no-follow ancestor checks, proves each lock has no conflicting byte-range owner, retains exclusive locks through the cutover, takes process snapshots before and after lock acquisition, and refuses on any inaccessible, changing or unexpected WakeHost candidate. The approved predecessor pointer, package bytes, target and event disposition must match the pinned store. If the historical connected store cannot be read or its target cannot be reconciled, migration remains held or follows a separately approved abandonment/rebind procedure; it cannot silently call the direct old Chat52 state Chat53.
5. A separate signed **package approval** binds the exact four candidate artifact bytes, manifest, source SHA, three GitHub Windows job IDs/run attempt, reviewer, protected root, selected first-generation anchor digest and generation. Exact-source CI is independently fetched by the broker before INTENT. Because V1 mandates a live PID and lacks an anchor digest, use an explicit V2 approval/ledger format for the offline case. Keep V1 replay readable, but do not reinterpret V1 fields or old records as first-generation authority.

## One guarded transaction

| Phase | Required retained proof | Durable result / failure behavior |
| --- | --- | --- |
| Admit | Fixed service/image/policy pins, operator admission, global ledger lock, independently signed anchor and package approval, exact CI, pinned predecessor/store/target, connected owner or offline locks | No INTENT on missing, ambiguous or changed proof. The one-shot service remains fail closed. |
| Stage | Exact candidate source and policy pins | Existing `STAGE_STARTED` then STAGED, with create-once marker, exact bytes/ACLs/object IDs and parent flushes. Residual stage requires attention. |
| Publish | Retained STAGED receipt and durable publication-attempt marker | Existing no-replace move, both parent flushes, retained moved-package proof and PUBLISHED. Any uncertain move is sticky attention; no automatic retry. |
| Old owner disposition | Original live-owner process pin with proved stop **or** all approved offline lock pins still held | A new phase record binds the observed disposition and old store/target identity. A stale process snapshot alone is insufficient. |
| Pointer and reader cutover | Exact old pointer and new published package pins; protected launch/status readers already deployed | One protected pointer switch with byte/object binding, parent durability and guarded reader readback. Any reader still selecting per-user `current.json` prevents activation. |
| New owner / complete | Exact protected package, process image/root/lock owner challenge, target and desired-state readback | Write new-owner and COMPLETE only after exact owner and one target generation are proved. On failure retain last-known-good and evidence; never replay an ambiguous `SUBMITTING` event. |

No caller-visible `true` flag or success-shaped diagnostic substitutes for a retained transaction pin. After a crash, resume only from exact durable ledger phase and exact physical/byte evidence; a matching pathname or same-byte replacement is insufficient. The lock and process proof must remain valid at every mutation seam, with the protected service itself the only writer.

## Minimum tests before any service enablement

- Canonical V2 signature rejects wrong key/domain, unknown/duplicate fields, altered anchor digest, stale time, wrong package/CI tuple, and live/offline field mixing. An unprovisioned or caller-supplied key never yields a policy-bound value.
- Offline fixture with two display paths aliasing one lock is handled by physical IDs; two distinct candidate roots, an inaccessible lock, lock conflict, late process, replaced root/lock/pointer, changed target, unknown event and missing connected store all refuse before INTENT unless the exact independent abandonment decision permits a different explicit path.
- Live fixture cannot use dev.84 process name/image/pointer alone as owner proof. PID reuse, process exit, different loaded image and split lock owner refuse.
- End-to-end first-generation fixture checks every phase and crash seam under the global lock, including parent-flush failure, pointer collision/swap, reader still on old namespace, failed new-owner challenge and exact last-known-good recovery. Run sudden-power-loss tests on the protected deployment filesystem separately from ordinary fixture tests.
- Provisioned-machine adversarial checks prove fixed service/image/policy/namespace identity and restricted-worker/descendant denial. Read back signed package, pointer, process/root/lock, target and one new uniquely identified Chat53 USER append before claiming installed Wake acceptance.

## Current decision

The source package publisher can be reused. No existing observation proves the first-generation connected predecessor, no V2 offline approval/anchor or protected provisioner exists, and no exact-source remote CI run accepts the current branch. The safe next implementation is the reviewed V2 anchor/approval and retained offline lock guard, followed by the first-generation ledger path and protected reader cutover. Leave the installer and service mutation holds in place until the independent design and provisioned-machine evidence are complete.
