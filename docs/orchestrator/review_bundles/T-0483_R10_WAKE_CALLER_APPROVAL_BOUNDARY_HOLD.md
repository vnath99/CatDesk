# T-0483 R10 — Wake caller approval boundary hold

**Date:** 2026-10-15. **Scope:** source review and isolated fixture evidence only. No installed WakeHost, signed CatDesk image, tunnel, browser, or live Wake store was changed.

## Finding

The Wake install object guard and host owner challenge answer **which physical store and live host** a candidate installer is addressing. They do not answer **who approved this candidate or this mutation**. The named-pipe challenge has a fresh nonce and checks the Windows-reported server PID, but the server does not authorize the client. The PID, root/lock fingerprint, staging name, and four SHA-256 hashes are caller-supplied or locally observable, not a review credential.

The isolated `wake/tests/install-store-authority-probe.ps1 -EnableOwnerProofHost` fixture starts a host that owns its test root and lock, proves the host through `install-authority-probe`, then calls `install-init` from a separate same-user test process. The command succeeds and creates `config.json` without any signed review approval. That is a useful ownership test, but it also characterizes the missing caller boundary. `publish-reviewed-install` accepts a staging manifest whose hashes the caller can compute. Its compiled script hash check constrains two scripts, not the caller-built host executable or an external review decision. `activate-reviewed-install` checks that it runs from the selected candidate image, but a candidate selected by self-consistent inputs is not independently approved.

The Wake root is under the interactive user's local application data. A same-user worker with unrestricted filesystem access could also write user-owned install objects directly, bypassing every check inside a newly built candidate CLI. A PowerShell prompt, environment variable, owner-only DACL, PID allowlist, candidate-embedded public key, or signed-envelope check executed only by that caller-built image would not make this an enforced boundary. The existing Ed25519 product trust root in `src/reviewed_build.rs` is scoped to the fixed **main CatDesk image** and its explicit signed purpose; it confers no Wake package authority. Its private key must remain outside CatDesk, Codex, MCP, and worker reach.

**Decision: hold P0 activation and natural canary.** The current source must not be described as safe from a same-user untrusted worker merely because root/lock ownership and package hashes agree. The live dev.84 host does not implement the new owner-proof protocol. Its physical root/lock differs from the direct caller's view, so even the new ownership preflight cannot authorize an install against it.

## Required boundary for a future install

1. Run all install mutation in an already trusted broker under an OS-enforced identity or integrity boundary. The worker must not be able to replace the broker, write its executable or policy, open its mutation endpoint as an authorized caller, or write the broker-owned package directory and active pointer directly. A worker-built candidate may supply inert bytes for review; it cannot be the authority that accepts itself.
2. Run native Codex and other untrusted workers with a proven restricted token, such as a tested AppContainer profile, whose effective token cannot write or retarget the Wake install namespace, host authority records, broker state, signing transport, or review receipts. Verify the actual child and descendants, all inherited handles, writable roots, filesystem aliases, and owner/ACL/integrity behavior with adversarial write probes. A `workspace-write` setting alone is not proof.
3. The trusted broker must require an independently issued, purpose-specific approval bound to the exact candidate package and operation. A signed envelope should canonically bind all four artifact digests, package identity/version, source and CI evidence, review identity, target physical store identity, and a monotonic/replay-safe generation. The broker must verify the signature with an independently controlled public trust root; only the offline signer holds the private key. Signature verification in a caller-built binary does not suffice.
4. Keep the package and active pointer under broker-only mutation through publication, stop, switch, restart, rollback, and crash recovery. The broker must pin the target's physical objects across the transaction and reconcile the actual host owner after restart. Do not infer authority from a displayed `%LOCALAPPDATA%` pathname or a hash supplied by the requesting process.
5. Migration from dev.84 requires a separately reviewed operator-controlled bootstrap of that broker and protected namespace. It must first reconcile the running host's exact root/lock and current Chat53 generation-34 target through read-only evidence. The current candidate's new checks cannot retroactively make dev.84 attest an owner-proof response or protect its user-writable install paths. If the live root remains divergent, fail closed and preserve the installed version and last-known-good package.

## Acceptance probes after implementation

- A same-user worker and its child cannot write, rename, hardlink, reparse, delete, or change ACL/owner on the broker, install directory, active pointer, signing transport, or host authority records. The worker cannot use a duplicated/inherited handle to do so.
- Calls with self-consistent hashes, a valid live PID/fingerprint, a copied old approval, a wrong-purpose signature, wrong physical store, altered artifact byte, stale generation, or unapproved source/CI evidence all fail before any install mutation.
- The approved exact package can be published once and retried idempotently after each crash seam; the broker alone performs and journals pointer handoff, verifies the new owner, and preserves the prior host on failure.
- The exact source commit passes local Windows adversarial fixtures and independent three-job CI. A real reviewed dev.85 install, one fresh diagnostic canary, and a natural review-ready Wake cycle are separate later evidence.

No fail-closed caller-auth code was added in this increment: a check placed in the current same-user, candidate-built CLI or installer script would be bypassable by direct store writes and could falsely suggest P0 was solved. The existing live-state hold remains in force.
